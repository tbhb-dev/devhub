# The runner pool role

The `actions_runner_pool` role runs a pool of ephemeral GitHub Actions runners on rootless Docker, one job per start of each slot's `systemd` user unit. `meta/argument_specs.yml` documents its options.

## Slot lifecycle

Each start of `actions-runner@N.service` has two phases, and `systemd` joins them, not a shell. Both phases are short linear scripts, without a wait on a background child and without a trap that cleans up. They share `actions-runner-slot-lib.sh`, which loads the settings and makes each API call. Its functions also request and revoke the installation token.

The start phase, `actions-runner-slot`, is the unit's `ExecStart=`. Its steps, in order:

1. Checks the settings, the token file, and the state directory. Next it prepares the Docker daemon. It pulls the pinned image if it's missing and removes a container that a killed run left behind. Last, it creates the slot's own network if that doesn't exist.
2. Exits 0 after a stop signal, before any credential exists.
3. Runs `actions-runner-slot-stop --pending` when an earlier start's cleanup is pending (see invariant 6). It exits 75 unless that cleanup resolved, and then exits 0 after a stop signal.
4. Reads the App's key with `op read` and signs a JSON Web Token (JWT) with it, then trades the JWT for an installation token.
5. Deletes this slot's offline, idle runners (see invariant 5).
6. Requests a single-use runner config. It records the runner's ID and the container's name, neither of them secret, as the slot's pending cleanup in `pending` in the unit's `StateDirectory=`.
7. Revokes the installation token, and exits 75 without a job unless GitHub confirmed the revocation (see invariant 3).
8. Exits 0 after a stop signal.
9. Replaces itself, through `exec`, with `docker run --rm --sig-proxy=true` and a container named `actions-runner-slot-N`. The runner config reaches the container's standard input through process substitution.

After the `exec`, the docker client is the unit's main process, and no shell runs beside it. Its exit status, the container's, decides the unit's result, but no exit status stops the restarts. A rate limit or a transient error exits 75 at once. For a rate limit, a `rate-limited` log line comes first, with its kind, primary or secondary, and any Retry-After value. Then `RestartSec=`, `RestartSteps=`, and `RestartMaxDelaySec=` set the delay before the next try. That delay starts at 10 seconds and roughly doubles up to 15 minutes, which allows about ten starts in the first hour.

Configuration errors stop the restarts through the unit's `ExecCondition=` line instead, which runs `actions-runner-slot --condition` before each start. It checks the settings, the token file, and the state directory, and exits 78 on any error. It also exits 78 while the state directory holds a `config-error` marker that's newer than both `pool.env` and the token file. The start phase leaves that marker, and exits 78, when GitHub refuses with a 401, with a 403 that isn't a rate limit and whose body is a GitHub error, or with a 404 for the installation or the runner group. Any other 403 exits 75 without the marker. After a condition exit from 1 to 254, `systemd` skips the start. The unit goes inactive with `ConditionResult=no`, and `Restart=` doesn't fire, so the operator's next start retries it. A changed `pool.env` or token file retires the marker, and so does removing it. The container never runs that check and can't write the marker, so its exit status can't stop the restarts. That's also why the unit has no `RestartPreventExitStatus=`. On `systemd` 259 that setting reads the main process's status, the container's after the `exec`. An `ExecStartPre=` failure doesn't trigger it either.

The stop phase, `actions-runner-slot-stop`, comes from the first `ExecStopPost=` line. Its steps, in order:

1. Takes the slot's lock without waiting (see invariant 6).
2. Classifies how the start ended, from `systemd`'s values and from whether a stop or restart job for the unit is running, which `systemctl --user list-jobs` shows. The start's outcome is `clean` after an exit 0 that no one requested a stop for. It's `stopped` after a requested stop, when the main process exited 0, 129, 130, or 143, or died of `SIGHUP`, `SIGINT`, or `SIGTERM`. It's `config-error` when the condition check skipped the start, and `failed` otherwise.
3. Removes the `actions-runner-slot-N` container with a bounded `docker rm --force`, which also stops a container that still runs.
4. Deletes the registration when the pending cleanup contains a runner ID and the container no longer exists. For that it requests a fresh installation token, sends the DELETE request, and then revokes that token. After a connection failure, a rate limit, or a server error, it retries the DELETE request, with at most four attempts within its deadline. A 2xx or a 404 resolves the registration. When the attempts run out, a `delete-failed` line logs the runner ID. A container that `docker rm` couldn't remove may still run a job. In that case the phase logs `delete-skipped` and leaves the registration alone.
5. Removes the pending cleanup once `docker rm` removed the container and the registration resolved, and prints one `job` line. That line contains the slot, the runner ID, the outcome, whether anyone requested a stop, whether a cleanup remains pending, and the `$SERVICE_RESULT`, `$EXIT_CODE`, `$EXIT_STATUS`, and `$INVOCATION_ID` values from `systemd`.

`SuccessExitStatus=129 130 143` lets a requested stop end clean even when the container passes on the stop signal's status. When no one requested a stop, the stop phase exits 1 after such a status, and `systemd` then counts the start as failed. It exits 75 while the container or the registration remains, or while another cleanup holds the lock, which also marks that start failed. Otherwise it exits 0. Only after a 0, and a main process that exited 0, does the second `ExecStopPost=` line reset the restart counter. That keeps the delay at its shortest for clean jobs.

Handlers for `SIGINT`, `SIGTERM`, and `SIGHUP` only record the first signal, and the start phase reads that record at steps 2, 3, and 8. With `KillMode=mixed`, `systemd` sends the stop signal to the main process alone. A stop lets the start phase finish the calls in flight, and nothing cuts the runner config request or the revocation short. In the job phase the docker client is the unit's only process. Rootless Docker runs the container under its own daemon's unit, and the stop phase removes it there.

Credentials stay in shell variables and pipes. `op` gets the 1Password token in its environment. `curl` reads the installation token or the JWT on its standard input as a config line. `docker run` reads the runner config from a pipe that process substitution opens, never from a here-document's temporary file. Argument lists, files, and log lines never contain a credential.

The design keeps these invariants:

1. `systemd` runs cleanup, through `ExecStopPost=`, once per start. It runs the stop phase after the main process ends for any reason, such as a finished job, a failed or skipped start, a stop, a timeout, a crash, or a `SIGKILL`. With `Restart=`, the next start begins only after the stop phase has ended, and a manual start waits for it too. The pending cleanup in the unit's state directory passes the runner ID and the container's name from one phase to the other.
2. Each token's DELETE requests come before its revocation. In the start phase, the token serves the stale runners' DELETE requests and the runner config request, and its revocation comes last. Any failure after the token request exits through `die`, which revokes the token. In the stop phase, the token serves the registration's DELETE requests, and its revocation comes last.
3. Each token gets at most one revocation request, and no token exists while a job runs. `revoke_token` forgets the token before its single request, with no retry. It counts the revocation as confirmed only after a 2xx, or a 401 or 404, which mean the token is already invalid. Before the `exec`, the start phase revokes its token, and a start whose revocation wasn't confirmed never runs a job. After a timeout, a 429, or a 5xx there, it logs `revoke-failed` and exits 75 without the `exec`, and the stop phase deletes the registration as usual, with a fresh token of its own. Only the start phase's shell ever held the unconfirmed token, and no container had it. It expires within the hour on its own, so later starts don't wait for it. Only after the main process has ended does the stop phase begin. It removes the container first and requests a token only once the container no longer exists. A token that another failed revocation or a `SIGKILL` left unrevoked expires the same way.
4. Each phase's stop latency has a bound, and the unit's `TimeoutStopSec=` outlasts both. `actions_runner_pool_cleanup_seconds` sets the stop budget, 120 seconds, and `TimeoutStopSec=` adds 15 to it. Before the first check, a stop waits for the current preflight call and the calls after it. Each `docker` call there ends within 25 seconds, and the image pull within 605. A `SIGKILL` at the timeout loses nothing there, since no credential or registration exists yet. Past the first check, a pending cleanup ends within the budget, and the check right after it ends the run. From that check on, the start phase ends within 115 seconds. That covers `op read`, the token request, at most 30 seconds of reconcile plus the call in progress, the runner config request, and the revocation. Both phases refuse a budget under that bound, which exceeds the stop phase's own least of 105 seconds. In the job phase, the docker client passes the `SIGTERM` to the container, and the runner shuts down at its own pace. If that outlasts `TimeoutStopSec=`, `systemd` sends `SIGKILL` to the docker client, and the stop phase removes the container. A stop that lands between step 8 and the container's start, inside the docker client's own startup, can lose its signal and ends that way too. The stop phase ends within the budget by its deadline. `systemd` applies `TimeoutStopSec=` to each `ExecStopPost=` command. After it, `systemd` sends `SIGTERM`, then `SIGKILL` after another `TimeoutStopSec=`.
5. The next start repairs a crash. A power loss, or a `SIGKILL` of the stop phase, can leave a registration behind. Each start lists the organization's runners after it gets the token and before it requests a runner config. It deletes every offline, idle runner named exactly `<prefix>-<host alias>-<slot>-<8 hex digits>` for its own slot. Prefixes can't contain a hyphen, the slot is all digits, and the random part has a fixed length. A name yields exactly one prefix, host alias, and slot, and a slot can't match another slot's or another pool's runner. The preflight also removes any container labeled with the slot.
6. A pending cleanup stays in place until it resolves. The start phase records it after the runner config response gives the runner ID and before it extracts the encoded config, as `pending` in `~/.local/state/actions-runner-slot-N`, the unit's `StateDirectory=`, which keeps it across a stop and a reboot. A `SIGKILL` between the registration and that record doesn't leave a pending cleanup for the timer to act on, and the next start's reconcile deletes the registration. A cleanup removes it only after it removed the container and the registration's DELETE resolved, so a failed `docker rm` or DELETE leaves it in place. The next start's step 3 retries it, and so do the next stop phase and `actions-runner-cleanup@N.service`, and none of them starts a job. A per-slot timer starts that `Type=oneshot` service every five minutes, and its `ConditionPathExists=` skips the run while nothing is pending. The service runs `actions-runner-slot-stop --retry` and nothing else. It ends within the stop budget and never starts the slot unit. A manual `systemctl stop` doesn't fire `Restart=`, so after one the timer removes a container that `docker rm` couldn't remove during the stop. Whichever path runs the cleanup takes an `flock` on `lock` in the state directory without waiting, and one that finds it held leaves the work to the holder. While it holds the lock, `--retry` acts only when the slot unit is inactive or failed, so never beside its start phase, job, or stop phase, which `systemd` already orders among themselves. A start that begins after that check finds the pending cleanup at step 3 and exits 75, because the retry holds the lock. No start records a new cleanup, or runs a container, before the retry has finished. A slot beyond the slot count keeps its timer, which does nothing while that slot has nothing pending.

This behavior needs `systemd` 254 or later, for `RestartSteps=` and `RestartMaxDelaySec=`. The Molecule scenario checks the rest on the image's own `systemd` with transient units. `ExecStopPost=` runs after a `SIGKILL` and sees the result in its environment, and `TimeoutStopSec=` ends it. Both a restart and a manual start wait for it. With `Restart=always` set, an `ExecCondition=` exit of 78 skips the start without a restart, and `ExecStopPost=` still runs and sees `exec-condition`. The slot unit cases check the condition and the cleanup timer on the installed units, and that `list-jobs` shows a stop job only during a requested stop.
