# About the server role

The `temporal_server` role runs Temporal 1.32.0 as one process with the frontend, history, matching and worker services, under the `temporal` user's rootless Docker daemon. `meta/argument_specs.yml` documents its options. The role pins the server and matching `temporalio/admin-tools` images by their public multi-architecture digests.

## Prerequisites

Apply `temporal_postgres` first. It owns `temporal_network_name`, normally `temporal`, and supplies the `temporal` account, its rootless Docker daemon, and the databases `temporal` and `temporal_visibility`. This role inspects the existing network and never creates it. Both databases remain unpublished on the host.

The predecessor role fixes the container name as `temporal-postgres` and the login as `temporal`. It also fixes the port at 5432. The defaults for `temporal_server_postgres_host` and `temporal_server_postgres_user` match those names. Set `temporal_server_postgres_password_file` to a managed-host file outside the user's home, readable by `temporal`, containing the same login password that the predecessor reads through `temporal_postgres_op_login_password`. The predecessor deletes its temporary password files after startup, so it doesn't supply this file. The playbook from issue 30 must retrieve this password from the password manager and provision this input file before applying the role. This role never calls a password manager. The database login must own both schemas and be able to migrate them.

Provision three `temporal_server_certificates` entries, named `ca`, `server` and `client`, with managed-host `cert_file` paths. Both leaves also need `key_file` paths. All source files must be readable by `temporal`. Only the public CA certificate belongs in the CA entry. For internode connections, the server certificate needs both server and client authentication usage, and a DNS subject alternative name matching `temporal_server_tls_server_name`. Client authentication usage must appear in the client certificate. Private certificate item references stay in the private provisioning inventory. This public role consumes the resulting files. Issue 34 covers certificate issuance and rotation separately.

## Startup and upgrades

The user unit runs the matching schema tool for both databases before every server start and requires their current schema versions to equal the versions in that image's migration directories. It initializes version tables on fresh databases and applies outstanding migrations. Any failure stops startup. Only then does it write the password-bearing server configuration to the user's runtime directory and start the server. Passwords enter schema-tool containers through standard input and stay out of Docker metadata, unit files and files under the user's home. The password-bearing configuration remains in the user's runtime directory until the unit stops. The persistent files under the `temporal` user's home have `temporal` as their owner.

Before an upgrade, take a database dump and change the release and both digests together, remembering that downgrading binaries alone doesn't undo schema changes. Undo a failed migration by stopping the unit and restoring that dump. Then pin the previous release and both previous digests and reapply. Removing the server requires running `systemctl --user disable --now temporal-server.service` and removing any remaining `temporal-server` container. Database state remains unchanged.

## Retention, transport layer security, and metrics

<!-- cspell:ignore slirp4netns -->

The role reconciles `coord` with 30-day retention and `coord-test` with 3-day retention, with archival off in both. It adds missing search attributes in each of them and rejects an existing attribute with a different type. By default, the list contains Keyword `CoordRepo`, `CoordKind`, `CoordState`, `CoordHostClass`, `CoordHarness`, `CoordMode`, and Int `CoordNumber`, `CoordRound`. A second converge leaves `coord`, `coord-test`, and their attributes unchanged.

Frontend and internode transport layer security require certificates from the configured CA. Internal clients verify the server name and CA. The role installs `slirp4netns` and a drop-in for the `temporal` user's Docker unit that selects it with RootlessKit's builtin port driver. The predecessor's pasta implicit forwarding exposes listeners on every host interface, even with Docker publications bound to `127.0.0.1`. This drop-in leaves the runner user's daemon unchanged. On a changed drop-in, the role stops Temporal, restarts its Docker daemon and PostgreSQL, then starts Temporal after the schema checks. Through rootless Docker, the role publishes only the frontend and Prometheus ports, on `127.0.0.1`. Internode ports stay inside the server container. By default, configuration through `dynamicConfigClient` is an empty mapping. It rejects history size/count and frontend/matching rate overrides.

This role owns `temporal_textfile_dir`, `/var/lib/temporal-textfile` by default, owned by `temporal` with mode `0755`. Its `temporal-server.prom` contains `temporal_cert_expiry_timestamp_seconds{certificate="ca|server|client"}` for the installed certificates. The collector from issue 31 and backup client from issue 32 must use this directory and separate `.prom` files. No private keys enter this directory.

## Molecule

The default scenario uses the repository's run-ID platform name and Docker API connection. Run it with a distinct `MOLECULE_EPHEMERAL_DIRECTORY` for this role, as `mise run test-ansible` does. Its sequence excludes check mode and includes `idempotence`, a previous-minor converge and an upgrade in `side_effect`. Prepare generates two disposable certificate authorities and signed test certificates locally. Verify builds a disposable `temporalio/admin-tools` image with Python for the internode handshake probe. It never accesses a real credential store.

The integration fixture passes placeholder `temporal_postgres_op_admin_password` and `temporal_postgres_op_login_password` references to the predecessor. Prepare installs a local stub that returns the same disposable password stored in `temporal_server_postgres_password_file`. Startup and the test probes read schema versions through `docker exec temporal-postgres psql`, using local socket access as `temporal`. Access as `postgres` creates and drops the test database without a schema. The scenario disables the optional Docker data image. On macOS, export `DOCKER_CONFIG=$HOME/.config/docker-agent` before running Molecule.

Both pinned 1.31.1 and 1.32.0 include history schema 1.19 and visibility schema 1.14. For this reason, the previous-minor assertions run in `side_effect` before the upgrade, and verify repeats them after it. These assertions read database state instead of depending on journal storage and user-unit metadata in the test container. Startup checks both versions before executing the server. Release numbers aren't SQL schema numbers. This minor upgrade runs migration checks without increasing either schema version. Verify also exercises refusal of a fresh database without a schema, `namespace` and attribute queries, valid/absent/wrong-CA frontend clients, an unauthenticated internode handshake, mounted configuration through `dynamicConfigClient`, probes through `127.0.0.1` and other host interfaces, and exact certificate expiry timestamps.
